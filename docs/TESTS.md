# Mira’s tests

What checks Mira, where it runs and how to run it. The latest results run by hand, dated, are in [testing/latest-results.txt](testing/latest-results.txt); each CI run keeps its own.

| Suite | System | What it covers | CI |
| --- | --- | --- | --- |
| `tests/Mira.Core.Tests` | any system (.NET 10) | everything that doesn’t need WPF | `ci.yml`, on Linux; its “Built-in Tailscale” tests also in `mac.yml`, with Mira.app’s signed node |
| `tests/Mira.Tests` | Windows | the previous suite, then the Windows app | `ci.yml`, on Windows |
| `tools/extension/check.mjs` | Node.js 22 + Jellyfin | the extension through its API, as the apps use it: party and guest gateway, Funnel guard, TorLink relay (fake agent), the iPhone app’s HLS, automatic subtitles (settings, then the loop over the whole library from a fake local OpenSubtitles; read-only media: kept by Jellyfin 10, “failed” in the log and a new try later on 12), TheTVDB order of a series (fake client), “Identify…” posters, `/Mira` and party pages, on Jellyfin 10.9, 10.10, 10.11, 12.1, 12.4 and `latest` (on Mondays); then `tools/extension/log.mjs`: fails on any error, any warning or any exception from the extension in Jellyfin’s log | `web.yml` |
| `Mira.exe` harnesses | Windows | screenshots, real player, Windows integration, TorLink | `ci.yml` (gallery only) |
| Mira.app harnesses | Mac | every screen and playback; “Built-in Tailscale” on a test Tailscale network | `mac.yml` |

## The two .NET test projects

They’re assertion executables, not `dotnet test` projects: each test is a name and a block of code, run one after the other by `TestRun`. A failing test shows its reason and the following ones run anyway; the final summary counts both, and the exit code is 1 if a test failed or if the filter keeps none. Each run works in its own folder, under `.artifacts/tests`.

```powershell
dotnet run --project tests/Mira.Core.Tests/Mira.Core.Tests.csproj -c Release                       # everywhere
dotnet run --project tests/Mira.Tests/Mira.Tests.csproj -c Release --no-build                      # Windows, after dotnet build Mira.sln -c Release
dotnet run --project tests/Mira.Core.Tests/Mira.Core.Tests.csproj -c Release -- --filter TorLink   # only the tests whose name contains this text (repeatable)
dotnet run --project tests/Mira.Core.Tests/Mira.Core.Tests.csproj -c Release -- --list             # their names, without running them
```

**`tests/Mira.Core.Tests`** (`net10.0`): one file per theme (`ConnectionTests`, `FamilyTests` (the home on the app’s side: home link, `/Mira/home` through a fake server, refusal and code, routing of the home’s node, node by the link’s key against the fake Tailscale), `LibraryTests`, `SyncTests`, `PlayerTests`, `UpdateTests`, `SupplyChainTests`, `TorLinkTests`, `RemoteDownloadTests`, `PhoneTests`, `AccessibilityTests`), brought together by `PortableTests`. It references Mira.Core and also compiles, by link, the files of the other projects that depend on neither WPF nor Jellyfin: `UpdateApplier`, `UpdateLock`, `Updater`, `MetadataCache` and `ShellRegistration` from the Windows app, `HlsPlaylists`, `ContentPolicy`, `WebFiles` and `TorLinkRelay` from the extension, `Profile` and `KeychainVault` from the Mac app (the keychain is replaced there by a stand-in). On Linux and macOS, a file “held” by `FileShare.None` can’t be tested: there it’s only an advisory lock.

**`tests/Mira.Tests`** (`net10.0-windows`, WPF) compiles all the files of `tests/Mira.Core.Tests` except its `Program.cs`, runs them first, then those that only pass on Windows: paths, hard links, DPAPI, firewall and elevated script (without elevation: the CI runner is an administrator), WPF controls (`Program.cs`, `DesktopSupplyChainTests.cs`). Options:

| Option | What it does |
| --- | --- |
| `--mpv-integration` | real libmpv on an authenticated HTTP stream: resume, pause, seek, sync. Needs libmpv, `.artifacts/lecture-test.mp4` (longer than 10 s) and the stand-in server `node tools/mock-jellyfin.mjs` (127.0.0.1:18096). |
| `--torlink-integration` | real TorLink in the pseudo-console, isolated state; installs Mira’s in a test profile if there isn’t one (nodejs.org and registry.npmjs.org). |
| `--jellyfin-live <profile>` | read-only check of a real server with the protected session of a validation profile: libraries and latest additions. |
| `--update-server <folder> <port> <version>` | fake GitHub on the loopback, for `tools/update-check.ps1`. |
| `--prepare-ui` | creates a made-up session in `.artifacts/mock-profile`. |

**Where to put a new test.** Without WPF: in `tests/Mira.Core.Tests`, in its theme’s file (a Windows app file without WPF can be linked there by the `.csproj`). Windows only (paths, hard links, DPAPI, WPF): in `tests/Mira.Tests/Program.cs`. Code shared by Windows and Mac goes in Mira.Core, where it’s tested everywhere.

## Jellyfin extension

Mira web was retired after 0.9.3 (its Node, Chromium and Safari tests with it). The extension is still checked against a real Jellyfin where it’s installed from its repository:

```bash
tools/web/media.sh <folder>                     # test media (ffmpeg)
node tools/web/setup.mjs <server> <media> <user> <password> [manifest url]   # fresh Jellyfin prepared through its API
node tools/extension/check.mjs <server> <user> <password> <folder>             # the extension through its API, no browser
for f in src/Mira.Jellyfin/Pages/*.js tools/web/*.mjs tools/extension/*.mjs; do node --experimental-default-type=module --check "$f"; done
```

`web.yml` does it on Jellyfin 10.9, 10.10, 10.11, 12.1, 12.4 and `latest` (on Mondays), with a fake TheTVDB plugin (`tools/web/fake-tvdb`, and its client under the real one’s name: `tools/web/fake-tvdb-client`), a fake OpenSubtitles (`tools/extension/fake-opensubtitles.mjs`, started by `check.mjs`, port 8767; `Mira.subtitles.json`, written before Jellyfin starts, points to it), the extension’s loops every 10 s (`MIRA_CHECK_TICK_SECONDS`), read-only media, then the log read by `docker logs jellyfin | node tools/extension/log.mjs`.

## App harnesses

They’re in `src/Mira.Desktop/Checks` and only run with an isolated profile (`--data`), most often with the demo (`--demo`). Each writes its result to its output folder. `dotnet build` compiles them (the `MiraValidation` property, true by default); the packages (`tools/package.ps1`) and `dist/Mira` (`tools/publish.ps1`) are built with `-p:MiraValidation=false`: these options then close Mira at once (code 2), and `package.ps1` refuses a `Mira.dll` that still contains the harnesses.

`--visual-check` needs a profile with a valid protected session, or `--demo`. The TorLink check opens a visible window and only sends real keystrokes if it’s in the foreground; it touches neither TorLink’s real state nor Jellyfin. With a video that has chapters, the player check also checks the skippable segments:

```powershell
ffmpeg -i .artifacts/lecture-test.mp4 -i .artifacts/chapitres.txt -map_metadata 1 -map_chapters 1 -c copy .artifacts/lecture-chapitres.mkv
```

Screenshots are taken on the window’s background (opaque). What needs a real Windows (elevation, Restart Manager, sleep, multiple screens, Narrator) is still to be tried by hand: see [VALIDATION.md](VALIDATION.md).
