# Signaler un problème de sécurité

Pour une vulnérabilité, utiliser **Security → Report a vulnerability** sur le dépôt GitHub. Ne pas publier de jeton, fichier `session.protected`, cache de bibliothèque ou mot de passe dans une issue publique. Si le signalement privé n’est pas disponible, ouvrir uniquement une issue demandant un canal de contact, sans détail exploitable ni donnée personnelle.

La version de développement publiée la plus récente est la seule version suivie. Il n’y a pas encore de délai de correction garanti. À partir de la 0.5.2, les copies installées se mettent à jour d’elles-mêmes (voir plus bas).

## Mises à jour automatiques

- Mira interroge uniquement l’API des releases GitHub du dépôt (`api.github.com`) et télécharge les fichiers de release depuis `github.com`, puis les serveurs de fichiers de GitHub (`release-assets.githubusercontent.com`, `objects.githubusercontent.com`), en HTTPS. Chaque redirection est vérifiée avant d’être suivie ; toute autre adresse est refusée. Aucun identifiant ni donnée de bibliothèque n’est envoyé : seulement l’en-tête `User-Agent: Mira/<version>`.
- Une version n’est installée que si `mira-update.json`, publié avec la release, porte une signature ECDSA P-256 valide d’une clé intégrée à Mira (`UpdateKeys.Trusted`), puis si le fichier téléchargé a exactement la taille et l’empreinte SHA-256 de ce manifeste. Une release non signée, modifiée, d’une autre version ou plus ancienne que la copie en cours n’est pas installée. Juste avant l’installation, le fichier est vérifié de nouveau, et pour une archive chaque fichier décompressé est comparé octet par octet au contenu de l’archive : un fichier modifié, manquant ou en trop la fait décompresser de nouveau.
- La clé privée ne quitte pas le PC du mainteneur : `tools/Mira.Release` la garde chiffrée par Windows (DPAPI, compte courant) dans `%APPDATA%\Mira Release`, hors du dépôt ; une copie de secours se fait avec une phrase secrète. DPAPI protège la clé d’une copie du fichier, pas d’un programme lancé sous le même compte Windows : signer depuis un compte réservé aux releases réduit ce risque. Sans cette clé, une nouvelle release n’est pas proposée aux copies installées. Une clé de secours, créée directement dans un fichier chiffré par une phrase secrète et gardé hors du PC (`keygen-backup`), la remplace si sa clé publique a été ajoutée à `UpdateKeys.Trusted` ; sans elle, une release signée par une nouvelle clé devrait être installée une fois à la main. `tools/Mira.Release` refuse de signer avec une clé absente de `UpdateKeys.Trusted`.
- La publication (`tools/release.ps1`) refuse de commencer tant que les releases immuables de GitHub ne sont pas activées sur le dépôt : elles seules empêchent de remplacer ensuite les fichiers ou le tag d’une release publiée, même depuis le compte du mainteneur. Elle vérifie aussi, avant de construire quoi que ce soit, que la clé de signature s’ouvre et figure dans `UpdateKeys.Trusted`.
- Elle signe en dernier. La release reste un brouillon, sans tag et invisible du public, pendant que les workflows de GitHub, lancés par le script sur `main`, y joignent l’image disque Mac et Mira web, construits depuis le commit du brouillon ; ils ne joignent rien à une release publiée ni à un brouillon fait pour un autre commit, et ne remplacent jamais un fichier déjà là. Le script n’accepte que des exécutions faites sur `main` à ce commit précis, et signe les fichiers qu’il télécharge de ces exécutions mêmes (pas ceux qu’il trouverait sur le brouillon) : la signature couvre ce que GitHub Actions a construit depuis ce commit. Il vérifie l’image disque contre son SHA-256 et le manifeste Jellyfin contre l’extension, signe le manifeste de toutes les plateformes, vérifie la signature contre `UpdateKeys.Trusted`, puis publie la release d’un coup, après avoir vérifié qu’elle a exactement ses 12 fichiers, chacun avec l’empreinte SHA-256 que GitHub donne égale à celle du fichier vérifié et signé sur le PC, ceux des workflows joints par GitHub Actions. Une fois la release publiée, il vérifie que GitHub la dit immuable et, avec gh 2.81 ou plus récent, son attestation (`gh release verify`).
- Les téléchargements attendent dans `data\updates`, dans le profil de la copie, et seule la dernière version proposée y est gardée. L’installation reprend le même chemin que la copie : installateur Inno Setup silencieux pour l’utilisateur courant, ou nouvel exécutable qui attend la fermeture de Mira. Pour un dossier, les nouveaux fichiers sont d’abord copiés à côté des anciens et écrits sur le disque, puis échangés par renommages, après un journal de l’échange ; en cas d’échec, les anciens reviennent, et une copie de retour arrière incomplète est gardée dans `data\updates`. Un échange coupé net (panne de courant) est annulé au démarrage suivant à partir de ce journal ; sa copie de retour arrière n’est effacée qu’ensuite, et reste entière tant que le journal ne peut pas être effacé. Le dossier `data` n’est jamais modifié ailleurs que dans `data\updates`. Mira attend la fin d’une installation en cours avant de démarrer. Aucune installation ne démarre pendant l’arrêt de Windows ; une installation qui échoue deux fois n’est plus relancée à chaque fermeture.
- Les exécutables restent non signés : la vérification de Mira ne remplace pas une signature Authenticode, et SmartScreen ne s’applique pas aux fichiers téléchargés par Mira lui-même.

## Mira web (extension Jellyfin)

- À partir de la 0.7.5, `mira-update.json` signé décrit aussi l’image disque Mac et l’extension Jellyfin (`others` : nom, taille, SHA-256). Les copies 0.5.2 à 0.7.4, qui ne lisent que les fichiers Windows (`files`) et ont toutes le même code de lecture, l’acceptent comme avant.
- Quand Mira pour Windows installe Mira web (Guide, **Mira sur ton téléphone**) ou fait avancer son dépôt (au démarrage qui suit une mise à jour de Mira, quand Jellyfin a déjà un dépôt de Mira activé et que le compte connecté gère ses extensions), il vérifie d’abord la release de sa propre version : GitHub la dit immuable (`immutable` de l’API des releases ; une release encore modifiable est refusée), la signature de `mira-update.json` par une clé de `UpdateKeys.Trusted`, la taille et le SHA-256 de `mira-jellyfin-X.Y.Z.zip`, puis `jellyfin-manifest.json` (l’extension Mira seule, dans cette version seule, téléchargée depuis cette release, avec le MD5 de l’archive vérifiée). Il met alors dans Jellyfin le dépôt de cette version précise (`releases/download/vX.Y.Z/jellyfin-manifest.json`) à la place de tout autre dépôt de Mira, sans toucher aux autres dépôts. Le guide fait ensuite installer l’extension et redémarre Jellyfin. Au démarrage, Mira ne fait que changer le dépôt, et seulement vers l’avant : rien si le dépôt de Mira propose déjà cette version ou une plus récente, ou si Jellyfin a déjà cette version de l’extension ou une plus récente ; il n’installe rien et ne redémarre rien, c’est la tâche de mise à jour de Jellyfin qui installe la nouvelle version, selon ses propres règles (une extension désinstallée, désactivée ou sans mise à jour automatique reste telle quelle). Si une vérification échoue, rien n’est changé dans Jellyfin : le guide dit pourquoi, et le démarrage réessaie au démarrage suivant.
- Ce qui n’est pas vérifié par Mira : Jellyfin télécharge lui-même l’archive, et ne contrôle que le MD5 du manifeste. Entre la vérification de Mira et ce téléchargement, et à chaque réinstallation, ce sont les releases immuables de GitHub qui garantissent que les fichiers de la release n’ont pas été remplacés : c’est pourquoi Mira refuse une release modifiable. Un dépôt ajouté à la main (`releases/latest/download/jellyfin-manifest.json`, la marche à suivre sans Mira pour Windows) n’est pas vérifié du tout par Mira : Jellyfin y installe la dernière version publiée, en faisant confiance à GitHub et au compte qui publie, pas à la signature de Mira.
- L’extension est du code que Jellyfin exécute avec ses propres droits sur le serveur : c’est pourquoi Mira la vérifie avant de la faire installer. Elle sert les fichiers de Mira web intégrés à sa DLL et relaie les listes de lecture HLS de Jellyfin ; elle n’écrit aucun fichier.

## Données traitées par l’application

- Le mot de passe sert à l’authentification Jellyfin et n’est pas conservé.
- Le jeton de session est protégé par Windows DPAPI, pour l’utilisateur Windows courant.
- Le dossier `data` contient aussi les préférences, un identifiant de périphérique, les images, le cache de bibliothèque et les événements de lecture en attente. Le cache n’est pas chiffré.
- Les échanges se font avec le serveur Jellyfin configuré. Le client envoie sa progression et ses changements de favoris/statut vu. Pour un serveur distant, utiliser HTTPS.
- Le protocole WebSocket Jellyfin requiert le jeton dans l’URL de connexion ; Mira ne journalise pas cette URL.
- Mira charge une bibliothèque native libmpv choisie sur le PC. Utiliser un moteur provenant d’une source de confiance. Celle que Mira installe (`data\mpv`) est une build figée par son empreinte SHA-256 ; quand une version de Mira en fige une plus récente, elle est téléchargée et vérifiée à côté, puis prend la place de l’ancienne au démarrage suivant. Un moteur choisi dans les réglages n’est jamais modifié.
- La page TorLink exécute TorLink avec Node.js. Celui que Mira installe (`data\torlink`, `data\node`) suit des versions figées : Node.js par l’empreinte SHA-256 de son archive officielle, TorLink et chacune de ses dépendances par le `package-lock.json` relu et fourni avec Mira (`npm ci`, empreinte sha512 de chaque paquet vérifiée, scripts d’installation désactivés). Les versions plus récentes figées par une nouvelle version de Mira sont préparées à côté et utilisées à l’ouverture suivante de TorLink. Un TorLink trouvé ailleurs sur le PC (raccourci, dossier global de npm) n’est pas vérifié par Mira : il n’est lancé qu’après une confirmation qui montre son dossier et sa version, ensuite mémorisée ; le cache de npm n’est jamais fouillé.
- Mira lit l’état de TorLink (configuration, historique, file, fichiers `.torrent`) sans le modifier. Un fichier `.torrent` de plus de 10 Mo, ou trop complexe, n’est pas lu. `data/torlink-imports.json` garde les noms et chemins des téléchargements rangés, sans lien magnet ; `data/webview2` est le profil du terminal intégré.
- Le terminal est une page locale sans accès réseau, qui n’échange avec Mira que du texte de terminal. Mira n’ouvre aucun port ; le jeton Jellyfin n’est transmis ni à TorLink ni à la page.
- TorLink reste un client BitTorrent : tant qu’il tourne, y compris Mira réduit, il se connecte à des pairs, écoute un port et peut demander au routeur de l’ouvrir (UPnP, NAT-PMP), selon ses propres réglages.
- Le rangement ne crée que des fichiers vidéo et sous-titres, dans les dossiers de bibliothèque. Il ne remplace jamais un fichier existant et ne déplace jamais un fichier qu’il n’a pas placé ; en mode déplacement, le téléchargement quitte le dossier de TorLink.

L’installateur, l’exécutable portable et l’archive ne sont pas signés : Windows SmartScreen peut demander une confirmation. Chaque fichier de release a son empreinte SHA-256 pour vérifier le téléchargement ; elle ne remplace pas une signature de l’éditeur. L’installateur n’a pas besoin des droits administrateur et n’écrit que dans le profil de l’utilisateur courant (`%LOCALAPPDATA%\Programs\Mira`, menu Démarrer, entrée de désinstallation). L’exécutable portable laisse .NET extraire ses bibliothèques natives dans `%TEMP%\.net`.
