# Security of Mira

> En français : [docs/SECURITY.fr.md](docs/SECURITY.fr.md).

## Reporting a problem

For a vulnerability, use **Security → Report a vulnerability** on the GitHub repository. Never post a token, a `session.protected` or `session.json` file, a library cache or a password in a public issue. If private reporting is not available, open only an issue asking for a contact channel, with no exploitable detail and no personal data.

Only the latest published version is supported. There is no guaranteed time to fix yet. Since 0.5.2, Mira for Windows updates itself (see below).

This document describes what each part of Mira does, from the code of the version in development.

No telemetry, no audience measurement. Everything Mira contacts (summed up in the app: **Settings → Privacy**, on Windows, Mac and iPhone, with the switch of each connection that has one):

## Mira for Windows

- The password is used for Jellyfin authentication and is not kept. The session token is encrypted by Windows DPAPI, for the current Windows user (`data\session.protected`).
- The `data` folder also holds the preferences, a device ID, images, the library cache (SQLite, not encrypted) and pending playback events. Caches are kept apart per server and per account; signing out first erases the local session, then asks Jellyfin to forget the token (`Sessions/Logout`, 3 s at most).
- `errors.log` keeps only the type of an unexpected error and the method involved, never its message (an HTTP error may contain credentials or private paths), 256 KB at most.
- Server found on the sign-in screen (as on Mac): any device of the home network can answer the discovery question, as for Jellyfin's apps. Mira only fills in the address, shown with the server's name, and checks it like a typed address before any password (public information, HTTP warning below). The list of Tailscale devices comes from `tailscale status --json`, run with your rights from Tailscale's installation folder (never from the PATH), only when Tailscale is connected on this PC.
- Signing in (as on Mac): an `http://` address that goes through the Internet (neither this PC, nor the home, nor Tailscale; an Internet name always counts as the Internet, whatever the network's DNS answers) is pointed out before the password is sent, which leaves only after **Sign in anyway**. For an Internet name, an HTTP answer is not kept if HTTPS failed on its certificate. No certificate validation is bypassed.
- libmpv is loaded without the current folder or the PATH, without mpv's configuration file (`config=no`); it gets the token through a header. With `https://`, mpv checks the server's certificate and name before sending anything (`tls-verify`), against only the authorities of the chains .NET accepted for that server during this run (`ServerTrust`, a `mira-tls-*.pem` file in the temporary folder, removed on quitting): a certificate Mira refuses is refused by the player too, which never receives the token. mpv never runs `yt-dlp` (`ytdl=no`), even when it is in the PATH.
- A single URL protocol, `mira://ensemble/<group>?server=<address>` (“Open in Mira” of a Watch together invitation), registered for the current user by the Start menu copy and removed on uninstall. The browser asks before starting Mira, which then reads nothing else from the command line (no `--data`, no test option) and refuses any link that does not have exactly this form (group ID, `http(s)` address without a user name). The link only offers a group, with **Join**: only a group of the open account's Jellyfin server; a group of another server opens, on request, in the browser; with no account open, the link's address is put in the sign-in form, visible, with the usual HTTP warning. The test options (`--update-feed`, `--update-key`) are read only with a `--data` profile and a loopback address.
- Authenticode signing of the Windows files: the code signing policy is in the README. No release is signed (the request for a free certificate from SignPath Foundation was refused on 2026-10-30; to be asked again later): SmartScreen may ask for confirmation. Each release file has its SHA-256 hash; it does not replace a publisher's signature. The installer needs no administrator rights and writes only to the current user's profile (`%LOCALAPPDATA%\Programs\Mira`, Start menu, uninstall entry). The portable executable lets .NET extract its native libraries to `%TEMP%\.net`.

## Built-in Tailscale (Windows)

To reach your Jellyfin from a PC without the Tailscale app, Mira can join your Tailscale network itself, as one more device.

- **Only when you ask.** Nothing goes to Tailscale before **Sign in to Tailscale**, which opens Tailscale's sign-in page in your browser; then the node starts with Mira, before its first request to Jellyfin, and stops with it. **Sign out of Tailscale** logs the device out of Tailscale, then erases its key and state from this PC; the device stays in Tailscale's console, “Logged out”, until you remove it there.
- **The program.** `mira-tailscale.exe`, beside `Mira.exe` (extracted from the portable executable into `data\app`), is a userspace Tailscale node (tsnet of Tailscale 1.104.4): no driver, no network adapter, no administrator rights. Mira starts it only after checking its SHA-256 hash (that of its build, the same once signed) and refuses a node from another version of Mira or one that could send logs to Tailscale (built without them: `ts_omit_logtail`, and it tells Tailscale it keeps none). A Windows job object ties it to Mira: it ends with Mira, even when stopped from Task Manager.
- **What it opens.** No service on your Tailscale network: it only calls out. Mira (requests, WebSocket) and mpv go through its proxy (SOCKS5 and HTTP) on `127.0.0.1`, protected by a random password drawn at each start: another program on this PC cannot use it to get into your network. The node reaches only the devices of your Tailscale network (any other address is refused), and Mira goes through it only for an address of that network: never for this PC, the home network, the Internet, nor what the Tailscale app connected on this PC already reaches.
- **Its state** (the device's identity on your network, its private keys) is encrypted with AES-256-GCM in `data\tailscale`, by a 32-byte key kept by Windows DPAPI for your account (`data\tailscale.protected`). A copy of these files on another account or another PC does not open.
- **Its log** (`data\tailscale\mira-tailscale.log`, 256 KB at most, one older beside it) stays on this PC and keeps no sign-in page: whoever opens a page that is still valid can add the device to their own Tailscale network.
- What Tailscale learns about the device is described by its [privacy policy](https://tailscale.com/privacy-policy) (in force on 25 August 2026): name, system, IP addresses, public key, version, connection times. The content of the traffic is end-to-end encrypted: Tailscale does not see it.

## Automatic updates (Windows)

- Mira queries only the GitHub releases API of the repository and downloads release files from `github.com`, then GitHub's file servers, over HTTPS. Each redirect (5 at most) is checked before being followed; any other address is refused. No credential or library data is sent.
- A version is installed only if `mira-update.json`, published with the release, carries a valid ECDSA P-256 signature from a key built into Mira (`UpdateKeys.Trusted`), then if the downloaded file has exactly the size and SHA-256 hash of that manifest. A release that is unsigned, modified, of another version or older than the running copy is not installed. Just before installation, the file is checked again, and for an archive each extracted file is compared byte for byte with the archive's content: a modified, missing or extra file makes it extract again.
- Downloads wait in `data\updates`, and only the last version offered is kept there. Installation follows the copy's own path: a silent Inno Setup installer for the current user, or a new executable that waits for Mira to close. For a folder, the new files are copied beside the old ones and written to disk, then swapped by renames, after a journal of the swap; if it fails, the old ones come back. A swap cut short (power failure) is rolled back at the next start from that journal. The `data` folder is never changed anywhere but in `data\updates`. No installation starts while Windows shuts down; an installation that fails twice is no longer retried at each close.
- SmartScreen does not apply to files downloaded by Mira itself: Mira's signature stands in for it for updates, not for the first download.

## Signed publishing

- The private key never leaves the maintainer's PC: `tools/Mira.Release` keeps it encrypted by Windows (DPAPI, current account) in `%APPDATA%\Mira Release`, outside the repository; a backup copy is made with a passphrase (PBKDF2). DPAPI protects the key from a copy of the file, not from a program run under the same Windows account: signing from an account kept for releases reduces that risk. A backup key (`keygen-backup`, kept off the PC) replaces it if its public key is in `UpdateKeys.Trusted`; otherwise, a release signed by a new key would have to be installed once by hand. `tools/Mira.Release` refuses to sign with a key missing from `UpdateKeys.Trusted`.
- `tools/release.ps1` refuses to start as long as GitHub's immutable releases are not enabled on the repository: they alone prevent replacing the files or the tag of a published release afterwards, even from the maintainer's account. Before building anything, it also checks that the signing key opens and is in `UpdateKeys.Trusted`.
- It signs last. The release stays a draft, with no tag and hidden from the public, while the workflows `windows.yml`, `mac.yml`, `web.yml` and `ios.yml`, started by the script on the `release/vX.Y.Z` branch made at that commit, attach to it the Windows files, the Mac disk image, the Jellyfin extension and the unsigned iPhone app, built from the draft's commit; they attach nothing to a published release nor to a draft made for another commit, and replace a file there only with the one from their own run (retry of an interrupted upload). The script accepts only runs made at that exact commit and signs the files downloaded from those very runs. It checks the Authenticode signatures of the Windows files (`tools/check-signed.ps1`: valid, from SignPath Foundation, timestamped), the disk image against its SHA-256 and the Jellyfin manifest against the extension, signs the manifest of every platform, checks the signature, then publishes the release at once, after checking it has exactly its 14 files, each with the SHA-256 hash GitHub gives equal to that of the file checked and signed on the PC. Finally it checks that GitHub says the release is immutable and, with gh 2.81 or later, its attestation (`gh release verify`).
- The Windows files are no longer built on the maintainer's PC: `windows.yml` publishes them on a fresh GitHub machine, sends SignPath only Mira's files (`Mira.exe`, `Mira.dll`, `Mira.Core.dll` and the portable executable, in an artifact of the run), which SignPath signs after the maintainer's approval, once it has checked that they come from this run of this repository (the action passes it the run's token) and carry the product name “Mira” and the release's version; the workflow puts the signed files back in the folder, builds the archive and the installer around them, has the installer signed the same way (second approval), checks each signature, then attaches the three files and their `.sha256` to the draft. The uninstaller made by Inno Setup stays unsigned (it does not carry the mark of the Internet). `release.ps1 -Unsigned` publishes without SignPath, as long as the project is not accepted.
- Since 0.7.5, `mira-update.json` also describes the Mac disk image and the Jellyfin extension (`others`: name, size, SHA-256). Copies 0.5.2 to 0.7.4, which read only the Windows files (`files`), accept it as before.

## Jellyfin on this PC (Windows)

- **Installation.** “Install Jellyfin on this PC” downloads Jellyfin 12.1's official installer, pinned by its address and SHA-256 (those of the winget manifest `Jellyfin.Server`). The file is reopened with shared read access only, its SHA-256 checked again on that open file, then started elevated (`runas`, `/S`) without having been closed: nothing can change it between the check and the start. It installs the `JellyfinServer` service, under Network Service. Jellyfin's wizard is finished with remote access from the Internet turned off.
- **Library folders.** Mira creates `Films`, `Séries` and `Animes` and gives Network Service read access (inherited) to these three folders only, not to the chosen folder: Windows lets any account traverse a folder down to a folder it can read. No need to be an administrator: you own them. A whole drive, a system folder, an account folder, Documents, the Desktop and OneDrive are refused. A file filed by TorLink (hard link or move) gets that right only if its folder already gives it. Copies 0.7.4 and earlier gave it to the whole chosen folder: `docs/INSTALLATION.md` says how to remove it.
- **Phones (“Prepare everything”).** Mira reads the service and the firewall without rights, then decides everything itself, without rights either: set the service to start automatically (a delayed start is kept) with three restarts after an error then nothing more (`sc failure`, `sc failureflag 1`), and an inbound rule “Mira - Jellyfin”: TCP, Jellyfin's `jellyfin.exe` alone, its port alone, from the local network (`localsubnet`) and Tailscale (100.64.0.0/10), plus UDP on the single port 7359 of Jellyfin's discovery, from the local network only (so that Mira on another computer finds it; the answer, a few dozen bytes, gives its name, its ID and its address), on **private and domain** networks only. On a public network (a café's Wi-Fi), `localsubnet` would be that of strangers, and Jellyfin counts their private addresses as local. A rule from an earlier version (`profile=any`) is tightened. The block rules for `jellyfin.exe` that stop the phone lose the home profile and Tailscale's (or are disabled if none is left); only rules naming `jellyfin.exe` are touched, and “Block all incoming connections” is never changed.
- **Public network.** A network Windows counts as public is made private only by the **Make private** button, when you say it is your home's (the same Wi-Fi adapter joins other networks); never a domain network, never by **Prepare everything** alone. A refusal from Windows is read back by Mira and told by the guide.
- **Elevation.** What needs administrator rights runs in System32's Windows PowerShell (`powershell.exe -NoProfile -NonInteractive -WindowStyle Hidden -EncodedCommand`), started with `runas`: a single Windows prompt, and nothing from Mira's folder (writable without rights) runs as administrator. The script is fixed: the plan's numbers are written into it as numbers, the texts (adapter and rule names, arguments) in base64, decoded by the script, never read as code. It uses only System32's `sc.exe` and `netsh.exe` and Windows' COM objects (firewall, WMI), no cmdlet or module (`$PSModuleAutoLoadingPreference = 'None'`: a module from the Documents folder would run as administrator). Mira then reads back itself, without rights, what was done. **Stop opening Jellyfin to the network** only deletes Mira's rule.
- **Updating Jellyfin.** Its version and its installer's SHA-256 hash come from the winget manifest `Jellyfin.Server` (reviewed by Microsoft's pipeline before publication), the installer from `repo.jellyfin.org` only (https, default port, name `jellyfin_<version>_windows-x64.exe`): both sources must agree. Mira downloads it into its profile and checks its hash; the elevated script checks it again on the file it keeps open with shared read access only until the installer ends, then starts it with `/S`: no program of the account can change it between the check and the start. The path is passed in base64, the hash as 64 hexadecimal digits. Never without a click on **Update Jellyfin** and Windows' prompt, never during playback, always after a successful backup; a new major version is called out as such.
- **Jellyfin backup.** Its archive (made by Jellyfin, in its data folder) contains the accounts' password hashes (PBKDF2), each device's sign-in tokens and the API keys in clear: whoever reads it can sign in to your Jellyfin as those devices. Mira says so beside the button and copies it only to the folder you choose; there it deletes only Jellyfin's archives (`jellyfin-backup-<date>.zip`) beyond the three most recent.
- **Tailscale.** “Allow Tailscale” adds 100.64.0.0/10 to Jellyfin's local networks (Jellyfin administrator account required); the rest of its network configuration is sent back as it is. Access from the Internet stays refused by Jellyfin.

## The Jellyfin extension

- **Verified installation.** When Mira for Windows installs the extension (**Guide → Mira on your iPhone**), Mira for Mac too (**Settings → Account & server**, Jellyfin restarted only once nobody is watching), or moves its repository forward (at the startup after a Mira update, if Jellyfin already has a Mira repository and the account manages plugins), it first checks the release of its own version: GitHub says it is immutable (a release that can still be changed is refused), the signature of `mira-update.json` by a key of `UpdateKeys.Trusted`, the size and SHA-256 of `mira-jellyfin-X.Y.Z.zip`, then `jellyfin-manifest.json` (the Mira extension alone, in that version alone, downloaded from that release, with the MD5 of the checked archive). It then puts in Jellyfin the repository of that exact version in place of any other Mira repository, without touching the others. At startup, it only moves that repository forward, never back, without installing or restarting anything: Jellyfin's update task installs the new version, by its own rules. If a check fails, nothing is changed in Jellyfin.
- **What Mira does not check.** Jellyfin downloads the archive itself and checks only the manifest's MD5. Between Mira's check and that download, and at each reinstall, GitHub's immutable releases are what guarantee the files have not been replaced. A repository added by hand (`releases/latest/download/jellyfin-manifest.json`, the way to go without Mira for Windows) is not checked by Mira: Jellyfin installs the latest published version there, trusting GitHub and the account that publishes.
- **The extension** is code Jellyfin runs with its own rights on the server. It serves its pages built into its DLL (`/Mira`, which says where to get the apps, and the page of a party link; for development, those of the folder named by the server's `MIRA_WEB_DIR` environment variable), with no possible path traversal, and relays Jellyfin's HLS playlists for the iPhone app's player: it asks Jellyfin itself for them, at an address taken from Jellyfin's settings and never from the request, then rewrites them; video, audio and subtitles always come from Jellyfin, which checks the `ApiKey` of each address. Its pages are public, like those of jellyfin-web, except `/Mira/torlink`, `/Mira/invites` and `/Mira/identify` (below). It writes no file.
- **Download on the server PC.** `/Mira/torlink` accepts only Jellyfin administrator accounts (`RequiresElevation`, like its dashboard): another account gets 403, and the apps do not show it the screen. The relay keeps everything in memory, with caps (pending requests, searches, results), and checks what it receives as Mira for Windows checks it again (`RemoteDownloads`, cases shared with the iPhone app): cleaned search, with no leading dash (TorLink would read it as an option), categories films, series or anime only; magnet link of 8 KB at most, with no control character, with a valid `btih`. The magnet links of results stay in the relay; the searching device gets none. A single Mira for Windows (the first online, under an administrator account) takes the work.
- **Posters of “Identify…”.** Jellyfin searches for a title itself from its sources (TMDb…); its suggestions give a poster's address on their side, and Jellyfin has no relay for these images. `/Mira/identify/image?url=` relays them so that neither the phone nor the computer contacts those sites: Jellyfin administrators only (`RequiresElevation`), HTTPS only, default port, no credentials in the address, to a closed list of hosts (`IdentifyImages`: image.tmdb.org, artworks.thetvdb.com, m.media-amazon.com, s4.anilist.co, cdn.anidb.net, cdn.myanimelist.net), redirect to another host refused, 15 s and 5 MB at most, answer sent back only if it is an image. These sites see the server's IP address, as when Jellyfin takes its posters there.
- **Pages.** Strict security policy: `script-src 'self'`, `connect-src 'self'`, `object-src 'none'`, `frame-ancestors 'self'`, styles from the file or allowed by their hash (no `'unsafe-inline'`), `Referrer-Policy: no-referrer`. What comes from the server (a party host's name, the title playing) is written as text, never as HTML.

## Guest links (Invite by link)

A Jellyfin administrator makes a link for someone with neither an account nor Tailscale; the guest opens it and watches with the host's group. What bounds it:

- **Only `/Mira` is open to the Internet.** Funnel is set to `--set-path=/Mira` towards `http://127.0.0.1:<port>/Mira`: the rest of Jellyfin (dashboard, API, sign-in) cannot be reached through Funnel. Windows' firewall and Mira's rules do not change (Funnel arrives through Tailscale, locally). Jellyfin's server decodes `%2e%2e` then normalises the path (`/Mira/%2e%2e/System/Info/Public` reaches `/System/Info/Public` there, checked on 12.1); Funnel, for its part, decodes and cleans the path (`path.Clean`) before comparing it with `/Mira`, since at least Tailscale 1.40: its path handling, copied from Tailscale 1.104.4 and put in front of a real Jellyfin 12.1, answered 404 to the 30 variants tried (`%2e%2e`, `%2E%2E`, `.%2e`, `..%2f`, `%2f` in `/Mira`, `//..`, double encoding, `..\`, `..;`, case, absolute form). Not yet tried on the real Funnel: that is what the check below does.
- **A belt in the extension.** A request that came through Funnel carries the `Tailscale-Funnel-Request` header, which Tailscale (1.72 and later) sets itself after removing the visitor's. The extension recognises it before all the rest of Jellyfin (`TunnelGuard`, first middleware) and lets it go only to Mira's pages (`/Mira`, a party link's page, their files) and to the `/Mira/guest/…` gateway; Jellyfin's WebSocket, which answers at any path, only to the gateway and with the session of an open link. Everything else answers 404, even if Funnel were open to the whole of Jellyfin (checked on 12.1). A home device that sent this header would only limit itself.
- **Link address checked.** When the address is given, at each link created (unless a check succeeded within 10 minutes) and in the background when the list is read, the extension tries it from the server as an Internet visitor would: this Jellyfin's public card (`System/Info/Public`, its ID) must answer through the gateway, and nowhere else, devious paths included, sent as they are (`TunnelCheck`). If Jellyfin answers outside Mira, no link is created and Mira says why. These attempts go to the PC's own Funnel address (through Tailscale), sending nothing else.
- **One link, one account, one device.** Each link has its own Jellyfin account, hidden, with a random password never shown, which can play and join a SyncPlay group, without creating one, and nothing else (no download, no deletion, no management, no live TV, one session at a time). It sees every library, because SyncPlay requires it. The first device that opens the link keeps it: another is refused. The link's code (16 random bytes) is kept in the server's `plugins/configurations/Mira.invites.json`, to show the link to the host again; the guest's token only by its SHA-256.
- **Removing means cutting.** Once the link is removed, or after 7 days without use, its account is deleted from Jellyfin: its sessions and its WebSocket drop at once (checked on Jellyfin 12.1), and the link no longer opens. To delete without a signed-in administrator, the extension creates at the first link an API key “Mira” (visible in the dashboard, **API Keys**); deleting it stops this clean-up until the next link.
- **Closed-list gateway.** The guest's page talks only to `/Mira/guest/…`, which relays to Jellyfin (on loopback) only the routes of `GuestRoutes`: a title's details and images by its ID, streams and subtitles, playback reports, SyncPlay clock and commands (without changing the queue). It rewrites the authorisation and the device ID, shows only the host's groups and refuses to join another; an administrator token is refused there. Known limit: a guest who knows the ID of another title can read its details and stream while their link lives.
- **The guest's token is a real Jellyfin token**, because SyncPlay's WebSocket requires one; it serves only this limited account and dies with the link. Opening a link is limited to 10 attempts per minute and per address (the one Funnel passes on), 60 in all.

## Mira for Mac

- The session token is kept in the login keychain (generic item “Mira”, one per profile); if the keychain refuses or is missing, in `session.json`, readable by your account alone (mode 0600, folder 0700). Mira is signed ad hoc: each version is another app for macOS, which would ask for keychain access once per version; only an Apple signature (Team ID) would avoid it: the keychain compares the program's “partition”, its hash (cdhash) for any other signature, even a self-made certificate. Built-in Tailscale's key is in the same item (`KeychainVault`), for a single question. Since the version after 0.9.4, when Mira installs its own update, the outgoing version writes its entries to `keychain-handover` (mode 0600, like `session.json` when the keychain refuses the token) and removes its item; the new one reads them at its first start, makes an item of its own, then deletes the file: no more question, and the item still trusts only the copy of Mira that wrote it. The file stays between the close and that first start. An update made another way (Homebrew, by hand) still asks the question once.
- Data lives in `~/Library/Application Support/Mira`. Automatic updates since 0.8.8: Mira contacts only GitHub (releases API, the release's files), requires the `mira-update.json` manifest signed by a key built into the app, and keeps the disk image only if its size and SHA-256 are those of its `others` entry (`mac`). The new Mira.app is copied from the image (`hdiutil attach -readonly`, `ditto`) beside the old one (`.Mira.app.update`), then checked: same bundle identifier, version announced by the manifest, ad hoc signature intact (`codesign --verify --deep --strict`). Mira removes the quarantine from that copy alone (`xattr -dr com.apple.quarantine`), since it checked it itself; a fixed `/bin/sh` script, which gets paths and version as arguments, waits for Mira to end, swaps the two folders by renaming (the old one put back if the second rename fails) and reports the result at the next start. Where Mira cannot write (disk image, App Translocation, a folder read-only for this account), nothing is replaced: the checked image is offered for a manual installation. No privilege elevation is asked for. Mira is signed only ad hoc, with no Apple developer account: macOS refuses to open it at first launch until you allow it (`docs/INSTALLATION-MAC.md`).
- The `mira://ensemble/…` protocol is declared by the app (`CFBundleURLTypes`) and handled as on Windows: a group offered with **Join**, nothing else.
- Avalonia's build telemetry is turned off in the project.
- **Built-in Tailscale**: as on Windows (section [Built-in Tailscale (Windows)](#built-in-tailscale-windows): only when you ask, no service opened, proxy on `127.0.0.1` with a password drawn at each start, encrypted state, local log without sign-in pages), with these differences. The `mira-tailscale` node is inside Mira.app (`Contents/MacOS`), signed with it; Mira refuses, at its first word, a node from another version or one that could send logs, and it stops as soon as Mira closes, even killed (its input closes). The 32-byte key that encrypts its state (`~/Library/Application Support/Mira/tailscale`) is kept in the keychain's “Mira” item with the session token (“Mira (Tailscale)” apart before 0.8.8, copied then erased), otherwise `tailscale.key` (0600, your account alone) as long as the keychain refuses it; an unreadable key (keychain locked, question refused) is never replaced. Mira never removes Gatekeeper's quarantine left on Mira.app: it gives the command to type.

## Mira for iPhone

- The session token is kept in the iPhone's keychain (`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`: no iCloud backup, no other device); **Sign out** erases it then closes the session on Jellyfin.
- Like Mira for Windows and Mac, the app talks to Jellyfin over HTTP at home and through Tailscale (`NSAllowsArbitraryLoads`); an `http://` address that goes through the Internet is pointed out before the password is sent, as on Windows and Mac. No certificate validation is bypassed.
- **Built-in Tailscale** (off until you turn it on): the same node as on Windows (tsnet of Tailscale 1.104.4, built without sending logs, `ts_omit_logtail`), linked into the app; no VPN profile, no extra entitlement. It runs while Mira is on screen, or while a title still plays in Picture in Picture, and stops otherwise. It opens no service on your Tailscale network and reaches only its devices. Mira passes it its requests (API, images, player, WebSocket) through a relay on `127.0.0.1:48096` whose every address starts with a secret of 24 random bytes kept in the keychain: another app on the iPhone cannot use it to get into your network.
- Its state (the device's identity on your network, its private keys) is encrypted with AES-256-GCM in `Library/Application Support/Tailscale`, a folder excluded from backups, by a 32-byte key from the keychain (`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`). Its log stays in that folder and keeps no sign-in page. Tailscale's sign-in page opens in an ephemeral session (`ASWebAuthenticationSession`, without Safari's cookies): your Tailscale password goes only through it. **Sign out of Tailscale** logs the device out of Tailscale; it stays in Tailscale's console, “Logged out”, until you remove it there.
- The published `.ipa` is not signed: AltStore Classic signs it on the iPhone with the Apple ID of whoever installs it (free certificate, 7 days). Its SHA-256 is published beside it, in the same immutable release; AltStore checks that the app's identifier and version are those of its source (`tools/site/altstore.mjs`).

## Video engine and TorLink (Windows)

- Mira loads a native libmpv library chosen on the PC: use an engine from a trusted source. The one Mira installs (`data\mpv`) is a build pinned by its SHA-256 hash; when a version of Mira pins a newer one, it is downloaded and checked beside it, then takes the old one's place at the next start. An engine chosen in the settings is never changed.
- The TorLink page runs TorLink with Node.js. The one Mira installs (`data\torlink`, `data\node`) follows pinned versions: Node.js by the SHA-256 hash of its official archive, TorLink and each of its dependencies by the `package-lock.json` reviewed and shipped with Mira (`npm ci`, sha512 hash of each package checked, install scripts disabled). Newer versions pinned by a new version of Mira are prepared beside and used the next time TorLink opens. `docs/ARCHITECTURE.md` (“Audit du lock”) explains the known npm advisory on `ip`. A TorLink found elsewhere on the PC (shortcut, npm's global folder) is not checked by Mira: it is started only after a confirmation showing its folder and version, then remembered; npm's cache is never searched.
- Mira reads TorLink's state (configuration, history, queue, `.torrent` files) and writes there, with TorLink closed, only a download folder if it has none and the pause of seeding for the downloads it moved. A `.torrent` file over 10 MB, or too complex, is not read. `data\torlink-imports.json` keeps the names and paths of filed downloads, without magnet links; `data\webview2` is the built-in terminal's profile.
- The terminal is a local page with no network access (CSP `default-src 'none'`, navigations, windows, downloads and developer tools refused), which exchanges only terminal text with Mira. Mira opens no port; the Jellyfin token is passed neither to TorLink nor to the page. Node and TorLink started in the page are attached to a Windows Job closed with Mira.
- **Downloads sent by your other devices** (option “Download from your other devices”, on Jellyfin's PC): a search runs `torlnk search` with its arguments as a list (no shell), a download goes through `torlnk serve`, TorLink's HTTP API, on 127.0.0.1 only and behind a random 256-bit token, passed to TorLink through its environment (`TORLINK_API_TOKEN`), never on the command line or on disk; Mira talks to it without a proxy. This windowless TorLink is the same program as the page's, started like it in a (hidden) pseudo-console and a Job Object: it stops with Mira. Mira passes to Jellyfin only names, sizes, states and sources, never a path on the PC.
- TorLink remains a BitTorrent client: while it runs, including with Mira minimised, it connects to peers, listens on a port and may ask the router to open it (UPnP, NAT-PMP), according to its own settings.
- Filing creates only video and subtitle files, in the library folders. It never replaces an existing file and never moves a file it did not place; in move mode, the download leaves TorLink's folder.
- **Look for a better version** (Jellyfin administrator) is the only exception, and only for the file of the title asked for. The relay hands the request only to a Mira for Windows that knows how to replace (an older one would keep it beside), one at a time per title. Before touching anything, Mira checks that the file is the one Jellyfin gives for that title, that it is in a library folder, on an internal drive (a Recycle Bin exists), and that it is alone (not several versions). The new video is read by the `ffprobe` installed with Jellyfin (beside its `ffmpeg` or `jellyfin.exe`, never another found in the `PATH`), arguments as a list, low priority, 2 min at most; it must last as long as the old one, within 2 %. Then it is put beside it (hard link or copy, `.mira-part`), the old one goes to Windows' Recycle Bin (`SHFileOperation` with undo, never a permanent deletion without Windows asking), and the new one takes its name. If the Recycle Bin refuses, the copy is removed and nothing has changed. Never during playback of that title nor while the file is open. `data\torlink-imports.json` records each step, to finish or say where the files are if Mira closes in the middle.
